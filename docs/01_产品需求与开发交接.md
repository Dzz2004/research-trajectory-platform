# 科研轨迹记录平台：产品需求与开发交接

版本：v0.1，2026-11-03。

本文件与同目录的 `02_轨迹形式化与提取规范.md` 是新项目的需求输入。两份文件独立于旧 HER Agent 项目，不要求复制旧代码、运行记录或科研知识库。

## 1. 要做什么

开发一个简单的前后端服务平台。研究者提交一篇自然语言科研过程总结，可以粘贴 Markdown，也可以上传 Markdown 文件。平台保留原文，把它整理为统一的结构化科研轨迹，供研究者检查、修订和导出。

核心流程：

```text
粘贴或上传文稿
  → 保存原文
  → 模型提取 + 程序校验
  → 查看输入、过程节点、关系和输出
  → 对照原文修订
  → 保存／确认
  → 导出 JSON 或 Markdown
```

平台负责记录和整理过程。它不替研究者开展新科研，不执行文献检索或实验，也不为了让轨迹完整而补写经历。

## 2. 核心形式化方案

采用以下几个概念，首版不扩大节点体系：

| 部分 | 含义 |
| --- | --- |
| 输入 | 目标、约束、已有信息、人为指定条件 |
| 思考／决策节点 | 提出或解释假设、比较候选、作出选择；记录依据和结论 |
| 动作节点 | 查文献、计算、实验、表征等；记录操作和返回结果 |
| 输出 | 方案、对假设的结论、否定性发现、新问题等，可以有多个 |
| 关系 | 时序先后、论证依赖、明确的并行关系 |

输入和输出不是第三、第四种过程节点。动作的结果放在动作节点里；候选及取舍放在思考节点里。

原文可能只有论证，没有历史过程；这仍然是有效提交。不能要求每篇文章都同时包含两类节点、所有输入字段或完整时间链。

## 3. 最重要的产品原则

### 3.1 忠实提取是默认行为

- 原文没说查过文献，不添加“查文献”动作。
- 没有实验结果，保留缺失，不生成正向或负向结果。
- 不因为某一构型是作者期望，就编造比较过程使其胜出。
- 可以压缩、改写和归纳原文明确表达的内容，但不得扩大适用范围或提高证据强度。
- 允许形成基于原文的低风险隐含理解，必须标记为“推断”，与直接提取区分，并可由用户删除；不能据此添加新的行动、结果、文献或时序。
- 自动结果始终是待核对草稿；模型不能替研究者点击“确认”。

### 3.2 不强行生成时序

正文顺序、论证顺序和实际时序分别处理：

- “先查阅资料，之后开展实验”：可提取时序。
- “因为材料易团聚，所以考虑固定”：可提取论证依赖，不自动提取历史时序。
- 同一段讨论两种候选，不等于执行了并行任务。
- 原文无法判断时序时，显示“时序未提供”；可以按原文出现位置排列阅读，但必须标明那只是展示顺序。
- 失败后重新比较，应记录新事件并关联之前的判断，不覆盖旧节点。

### 3.3 产出不必等于验证成功

“提出 Au 均匀附着孔壁的构型方案”已经可以是一项产出，其状态可以是“提出、待验证”。不强制推演到完整配方、实验成功或性能改善。

作者给出的经验、解释、假说或条件性结论，不得自动显示为平台认可的科学事实。

### 3.4 缺失是结果的一部分

结果页显示缺失信息和可供贡献者补充的问题。缺失本身不等于提取失败，也不强迫用户立即补齐。

例如：“选择 Au 而非其他材料的依据未记录”“尚不清楚这一信息来自文献还是实验”。提问只针对有用的缺口，不要求贡献者补写一套理想研究流程。

## 4. 首版范围

### 必须实现

1. Markdown 文本粘贴、`.md`／`.markdown` 文件导入和预览。
2. 原文持久化；生成期间刷新页面仍可查看状态。
3. 调用一个可替换的模型适配层，生成结构化草稿。
4. 程序校验格式、引用、关系和基本一致性；错误可理解、可重试。
5. 结果页：输入、输出、过程节点、关系、来源定位及缺失问题。
6. 节点和关系的人工编辑、增删，以及输入／输出的修订。
7. 保存草稿和显式确认；编辑确认后的内容会回到待确认状态。
8. JSON 和 Markdown 导出；保留来源、推断／补充标记及确认状态。
9. 简单记录列表，能够重新打开之前的记录。

### 首版暂不实现

- 自动检索文献、连接实验设备、自动科研或多 agent 编排。
- PDF、Word、图片、OCR 和音视频导入。
- 多人实时协作、机构管理、复杂账户权限体系。
- 自动生成“真实历史”中不存在的步骤、结果或文献。
- 科学正确性自动裁决、agent 基准成绩或完善评估平台。
- 精确时间戳、持续时间和跨任务部分重叠的甘特图。

模型用于整理，相关功能不应依赖领域专用的固定流程节点。

## 5. 页面与交互

### 5.1 记录列表

显示标题、创建时间、提取状态、核对状态。提供“新建记录”和打开记录；首版不需要统计大屏。

### 5.2 新建／提交

- 标题可选，未填时从正文生成可编辑标题。
- 提供“粘贴内容”和“上传 Markdown”两个入口，最终走同一内容提交接口。
- 上传后显示文件名、可编辑的提交前正文和预览；提交的正文成为不可覆盖的原始版本。
- 可选注明文稿来源：研究者总结／AI 总结／模拟示例／不确定。未选为“不确定”，不要自动认定内容是真实执行记录。
- 原文中的科学机制主张不要求用户逐项预填标签。
- 文件和文本均要求 UTF-8 文本；文件解码失败给出明确错误，不生成乱码轨迹。
- 建议首版输入上限为 30,000 个 Unicode 字符，做成服务端可配置项；文件入口同时设置可配置字节上限，默认 256 KiB。前后端提示一致，不静默截断。
- 不执行 Markdown 中的原始 HTML，不自动访问正文中的外部链接或图片。

### 5.3 提取状态

```text
pending → running → succeeded
                 ↘ failed
```

失败时保留原文和已有人工版本，显示失败阶段与简要原因，允许用户显式重试。网络失败不能改用模拟数据并显示成功。短暂轮询即可，不要求 WebSocket 或专用队列平台。

### 5.4 结果与核对

推荐布局为“原文＋结构化结果”。窄屏上下排列，不要求复杂拖拽画布。

结果依次显示：

1. 输入：目标、约束、已有信息、人为条件。
2. 输出：产物类型、内容及其陈述状态。
3. 过程图／节点列表。
4. 信息缺口与补充问题。

节点点击后显示类型、内容、选择依据或操作结果，以及原文出处；原文定位使用行号和精确片段。对“推断”“人工新增”“模拟内容”使用文字标签。

提供两种互补阅读方式：

- **过程图**：时序自上而下；同一明确并行组内的任务同行；论证关系使用不同线型及文字标签。支持关系不得自动成为时序边。
- **节点列表**：所有节点可读、可编辑。只有论证关系、没有时序的节点放在“时序未提供”区域，按原文位置列出。不同无关节点不能仅因布局在一行就被称作并行。

V1 可以先使用简单图组件或按行布局，不以拖拽编辑和自动布局精美为验收前提。

### 5.5 编辑与确认

- 所有模型字段均可修订，原文不变。
- 模型直接提取的内容保留原文定位。
- 用户新增事实标为人工补充；用户自行构造的示意情节标为模拟。
- 改变原意后不能沿用失配的原文引用。修改应更新出处或标记为人工补充；单纯换一种说法且意思不变可以保留引用。
- 编辑后进行与自动生成相同的结构校验，不允许悬空边或伪造的原文片段。
- 确认前展示未解决缺口；用户可以确认“这忠实表达了我的总结”，不必补齐所有未知。
- 确认只代表贡献者核对，不代表实验已验证或平台认证科学正确。

## 6. 后端与持久化建议

技术栈可由新项目选择。要求前后端共享同一份轨迹契约；后端承担模型调用、校验、持久化和导出，不将模型访问凭据放到浏览器。

建议最小存储对象：

| 对象 | 保存内容 |
| --- | --- |
| Submission | 原文、输入方式、原文件名、文稿来源说明、内容哈希、创建时间 |
| ExtractionAttempt | 尝试ID、状态、关联提交、模型／提示词／契约版本、原始模型响应、校验错误 |
| TrajectoryRevision | 结构化 JSON、版本号、生成／人工修改来源、核对状态、保存时间 |

首版使用单工作区和简单持久数据库即可。保留旧版本可直接存完整 JSON，不要求实现复杂差异系统。

同一提交同时只允许一个提取尝试运行。重试创建新的尝试；重新提取的内容成为新草稿，不直接覆盖人工确认版本。模型原始响应只用于诊断，不作为未经转义的页面内容展示。

## 7. API 契约建议

这是行为契约，具体路由可以调整，但前后端应一致。

| 方法与路径 | 行为 |
| --- | --- |
| `POST /api/trajectories` | 保存提交并启动一次提取；返回记录ID、尝试ID和状态 |
| `GET /api/trajectories` | 返回记录摘要列表 |
| `GET /api/trajectories/{id}` | 返回原文、提取状态、当前草稿和最近确认版本信息 |
| `POST /api/trajectories/{id}/extractions` | 显式重新提取，创建新尝试；已有运行中尝试时拒绝重复启动 |
| `PUT /api/trajectories/{id}/draft` | 以 `base_revision` 提交整份修订，校验后创建新草稿版本；版本冲突返回409 |
| `POST /api/trajectories/{id}/confirm` | 确认指定草稿版本；不能确认结构校验不通过的版本 |
| `GET /api/trajectories/{id}/export?format=json&revision=...` | 导出指定版本；`format` 还可为 `markdown` |

上传 Markdown 可在浏览器读取 UTF-8 内容，然后与粘贴内容一样提交 JSON，同时保留文件名与输入方式；无需为首版增加文件对象存储服务。

提交请求示例：

```json
{
  "title": "Au 孔壁构型的研究总结",
  "input_kind": "markdown_file",
  "filename": "research_notes.md",
  "narrative_origin": "researcher_summary",
  "content": "# 研究总结\n……"
}
```

输出响应要区分格式错误、内容过长、模型连接失败和模型输出不合约。提取内容稀疏但有效时应成功返回草稿和缺口，不返回服务器错误。

## 8. 模型提取流程

```text
接收并保存正文
  → 生成用于定位的行号视图
  → 调用模型提取
  → 解析结构化返回值
  → 校验ID、字段、来源、关系
  → 如有结构错误，最多一次携带错误清单的修复
  → 保存草稿，或保存失败原因
```

修复只能解决格式、引用和一致性问题，不能给源文增加科研经历。二次失败后停止，允许用户查看简要问题并重试，不无限循环消耗调用。

模型适配层建议只暴露 `extract(content, extraction_rules, schema)` 之类的接口。保持提供方可替换；不把固定模型名称写进产品流程。实际模型配置与测试可在新项目实施时确定。

## 9. 验收场景

1. 粘贴 Markdown 与上传相同 Markdown，得到语义一致的结果，输入方式与文件名分别保留。
2. 输入只有设计论证，没有历史行动时，只提取思考节点及有依据的关系；不补实验、检索、时间链。
3. 输入明确写“先查文献，随后做实验”，提取两个动作及其先后；没有结果的动作仍保留空结果。
4. 输入明确写“文献检索和结构整理并行”，才建立并行关系。
5. “方案 A、B、C”保留在比较节点内，不生成三个已执行动作。
6. 人为固定 Au 能作为输入条件；不能展示为系统自主发现。
7. 输出“Au 均匀附着孔壁的构型方案”，标为提出方案；不要求编出性能验证。
8. 原文只是发光改善，不输出“产氢已提高”。
9. 原文明确为模拟记录，导出时仍保留模拟性质，即使用户已确认。
10. 每条直接提取的输入、节点、输出和关系都能定位到真实原文片段。
11. 时序不明时仍能成功保存，在界面明确显示；论证依赖不被布局算法变成历史顺序。
12. 人工编辑后来源标记正确，旧版本可保留，确认状态回到草稿。
13. 模型失败保留原文和人工版本，不伪装成功，不静默换演示数据。
14. 导出的 JSON 与 Markdown 来自同一指定版本；Markdown 保留类型、关系、来源、未知和核对状态。
15. 重新提取不覆盖确认版本；同版本并发编辑能发现冲突。

验收既包括正常操作，也包括空输入、超限输入、模型非法 JSON、悬空关系和校验失败。用有辨别力的少量样例验证即可，不追求测试数量。

## 10. 建议开发顺序

1. 先按第二份文档实现数据类型、校验器和两个固定输入样例。
2. 完成“提交→保存→返回结构化草稿→列表重开”的纵向流程。开发夹具要显式标记，不能冒充模型结果。
3. 接入模型，完成来源引用与忠实提取校验。
4. 增加输入／输出展示、节点列表、简单关系图和缺口展示。
5. 完成人工编辑、确认、版本及导出。
6. 按上述场景验收，优先解决错加事实、错认时序和来源丢失。

## 11. 可交给新项目的启动说明

> 请阅读两份文档，开发科研轨迹记录平台。输入为粘贴的自然语言／Markdown 或上传的 Markdown 文件，输出为忠实于原文的结构化轨迹。核心只有输入、两类过程节点、输出和三类关系。不要沿用旧 HER workflow，不要自动补写研究经历，不要把论证顺序变成历史时序。先跑通可保存、可核对、可导出的最小前后端流程，再接模型和完善关系展示。以本文件第9节及第二份文档的语义规则验收。
